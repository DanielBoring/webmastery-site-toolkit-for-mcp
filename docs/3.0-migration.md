# 3.0 migration guide (unreleased development)

This guide describes breaking changes being prepared after **2.6.0**. It does not
announce a 3.0 release or change the plugin header/stable tag. Deploying this
development branch requires updating clients before use.

## Bounded list windows and summary projection

This deliberately replaces exact filtered pagination for `list-posts`,
`list-pages`, generated `list-cpt-*`, `list-media`, `list-orphaned-media`,
`get-seo-scores`, and `get-readability-scores`. No ability name or capability
floor changes. The WordPress ability logical result (inside the Adapter's
existing success wrapper) is:

```json
{"success":true,"data":{"items":[],"page":2,"per_page":20,"next_page":3}}
```

| Logical field | Type | Meaning |
| --- | --- | --- |
| `items` | array of the ability's authorized item objects | Zero to `per_page` visible results from this candidate window |
| `page` | integer, at least 1 | Requested candidate-window number |
| `per_page` | integer, 1-100 | Maximum candidates checked, not visible-result count |
| `next_page` | integer or null | Next candidate window, or null when no lookahead exists |
| `total`, `total_pages` | absent | Exact filtered counts are no longer computed or exposed; no estimates replace them |

Score results keep `yoast_active` and their other existing provider/note fields.
When Yoast is inactive they return no items and `next_page:null`, with the same
pagination field types. Metadata permissions are evaluated for each candidate
before reading its score; filtering is within the window, never a global
score-filtered total. Existing analysis unknown/unevaluable behavior is unchanged.

Client migration: retain all filters, order, and `per_page`; begin with `page:1`,
process the returned `items`, then use `next_page` verbatim until it is null.
Do not stop when `items` is empty or shorter than `per_page`. Sparse and
all-denied windows are valid successes, and their continuation does not reveal
denied IDs or a denied-item count. Remove UI "page X of Y" assumptions and any
dependency on exact totals. Other list abilities retain their existing contracts.

The query requests at most `per_page + 1` IDs with `no_found_rows`, using the
explicit offset `(page - 1) * per_page`; the lookahead is consumed on the next
window, not skipped by a larger stride. Only the first `per_page` distinct IDs
are authorized/normalized. Existing primary ordering gains a same-direction ID
tie-breaker (`orderby:"id"` maps to WordPress `ID`). Sticky-post promotion is
disabled so it cannot expand or reorder a bounded candidate window. Search,
type/status/author/category/MIME/date filters and object/status/key authorization
remain applicable; there is no overfetch loop to fill a visible page.

The offset `(page - 1) * per_page` and successor `page + 1` must fit the
server's PHP integer range. Unrepresentable pagination returns `invalid_input`
before querying or priming; there is no arbitrary smaller page cap.
New SQL failures during candidate lookup or bounded object/term priming return
`upstream_failed`, without SQL diagnostics, rather than a successful empty EOF.
An old database error alone does not invalidate a warm, SQL-free cache hit.
On a newly detected SQL failure only, the current blog's post-query cache
generation is advanced so WordPress cannot reuse a failed query cached as empty.
This rare failure path invalidates other post-query entries for that blog too;
it does not flush the object cache or change normal successful-query caching.

`list-posts`, `list-pages`, generated `list-cpt-*`, and `list-revisions` gain the
strict string enum `fields:"summary"|"full"`, default `"summary"`. Summary
**omits** `content`; it does not substitute `""`, truncate or sanitize stored
values, or add a marker for an absent field. Full preserves the stored
HTML/blocks/backslashes/quotes exactly as earlier normalization did. Excerpt and
all other fields retain their original values/types. Get/write/restore responses
remain full. Media, scores, and orphan items already omit content and do not gain
the parameter. Revision lists keep `data.post_id`, `data.type`, and
`data.revisions`, the existing per-page cap, and no new continuation contract.
Invalid enum values, case variants, nulls, arrays, and wrong types must fail
before queries via the shared registration validator (the reviewed #126 source
dependency is included; its runtime acceptance remains separately gated).

Orphan checks use a candidate-restricted `_thumbnail_id IN (...)` query and
aggregate literal URL/GUID matches in chunks of at most 50 patterns (at most two
per attachment). The same batch helper backs single-media deletion. Each known
hit is mapped back to its own attachment; a database error/null result fails
closed, including `force:true`. The known-reference scope is unchanged: it is
not a universal proof of non-use and does not inspect arbitrary serialized
settings, transformed image URLs, or external sites.

**Limits:** windows are not transactional snapshots. Concurrent inserts, edits,
deletions, or permission changes may shift offsets and require a restart or
client-side deduplication. SQL offset/search work and reference scans can still
scale with table size; bounded PHP candidates/query counts do not imply constant
database time. Summary payload size is not universally capped: excerpts, titles,
terms, and third-party filters may be large. The 64-KiB default-summary and
64-MiB incremental-memory targets are measurements on a controlled fixture, not
production response guarantees. Real-runtime/package evidence remains a release
gate, separately from unit and static checks.

## Record-relative source markers

Authorized content, comment, media, user/audit, SEO and hygiene records add
`untrusted_fields`, a JSON array of unique field names relative to that record,
not paths from the response envelope. Marker order is not a client contract.
Only allowlisted fields actually present are marked, including present null,
false and empty values. Missing fields are not invented or marked.

For example, post summaries mark `title`, `excerpt`, `slug`, `url` and
`author_name`; full post records additionally mark `content`. Revision markers
belong on each `data.revisions[i]`, not `data`; full revisions mark
`author_name`, `title`, `content` and `excerpt`. Summary revisions omit both
content and its marker. Orphan/no-featured-image items mark `title` and `url`;
stuck-scheduled items also mark `author_name`.

Markers do not recursively modify stored maps, rewrite HTML or inspect nested
error-shaped data. Existing field values/types, object/key permissions and
canonical errors remain unchanged. Compact trash results (`id`, `status`) and
error objects are unmarked. All retrieved data remains untrusted even without
a marker: these annotations are not sanitization, an authorization grant,
proof of human approval, or a prompt-injection prevention guarantee.

## Canonical errors

Every registered Webmastery ability execution failure has this envelope:

```json
{"success":false,"error":{"code":"invalid_input","reason":"invalid_meta_key","message":"Invalid metadata key.","details":{}}}
```

`code` is one of the seven categories below. `reason` is the more specific
machine-readable discriminator. `message` is a human diagnostic, not a parsing
contract or an instruction. `details` is always a JSON object, including when
empty. Do not assume details are present beyond documented operation context.

| Canonical code | Legacy reasons retained under `error.reason` |
| --- | --- |
| `forbidden` | `forbidden`, `missing_capability`, `network_admin_required`, `protected_meta_key`, `metadata_not_writable`, `ability_invalid_permissions` |
| `not_found` | `not_found`, `plugin_not_found`, `target_not_found` |
| `invalid_input` | `invalid_*` input reasons (except those listed separately below), `file_too_large`, `missing_post_id`, `missing_scheduled_date`, `missing_target`, `scheduled_date_too_soon`, `ability_invalid_input` |
| `precondition_failed` | `precondition_failed`, `content_hash_mismatch`, `block_hash_mismatch`, `content_type_mismatch`, `trash_disabled`, `dependency_failure`, `network_context_required`, `site_kit_unavailable`, `site_kit_module_unavailable`, `site_kit_module_inactive`, `site_kit_module_not_connected`, `invalid_upload_limit` |
| `conflict` | `conflict`, `ambiguous_target` |
| `unsupported` | `unsupported`, `unsupported_mime_type`, `unsupported_type`, `site_kit_unsupported` |
| `upstream_failed` | `upstream_failed`, `external_error`, `content_hygiene_query_failed`, `database_health_query_failed`, `create_failed`, `delete_failed`, `download_failed`, `featured_image_failed`, `meta_write_failed`, `metadata_update_failed`, `restore_revision_failed`, `restore_failed`, `site_kit_invalid_response`, `site_kit_request_failed`, `status_update_failed`, `trash_failed`, `update_failed`, `upload_failed`, core output/callback/configuration failures |

The exhaustive mapping is in `Webmastery_MCP_Response::legacy_error()` and is
independently pinned by `tests/e2e/error-contract-assertions.php`. The destructive
interlocks below use `missing_confirmation` and `media_in_use` as precondition
failures and `too_many_ids` as invalid input. Combined metadata input uses
`metadata_requires_separate_call` as invalid input.

Two formerly generic stale-hash failures now use `content_hash_mismatch` and
`block_hash_mismatch`. Combined metadata authorization rejection, formerly
`meta_write_failed`, uses `forbidden` / `metadata_not_writable`; an actual storage
write failure remains `upstream_failed` / `meta_write_failed`.

## Old/new input, output, default, and permission matrix

| Surface | 2.6 behavior | Unreleased error-contract behavior | Input/default/permission impact |
| --- | --- | --- | --- |
| Operation failure | String error, structured code/message, or native `WP_Error`; sometimes top-level `data` | Canonical envelope; safe failure context in `error.details` | No input or default changes from error normalization |
| Successful single operation | Existing `success:true,data` payload | Unchanged, including nested data that resembles an error | No capability changes |
| Registered `WP_Ability::execute()` | Native schema/permission/callback errors mixed with plugin arrays | Owned subclass calls parent once and converts failures | Core schema validation, permission redaction, before/after actions remain; no permission replay |
| Native `check_permissions()` | `true` or `WP_Error` | `true` or marked `WP_Error`; canonical code, JSON envelope message, `data.webmastery_error` and HTTP `status` | Never return a truthy error array from permissions; meaningful native status retained |
| Core schema/permission diagnostics | May quote input values, schema details, or ability name | Fixed safe messages; `ability_invalid_input` / `ability_invalid_permissions` reasons | No disclosure of private submitted values; no bypass of original decision |
| MCP gateway failure | Can be success-wrapped, with `isError:false`, or lose error code | `isError:true` and canonical JSON in one text content block | Same authenticated endpoint/account/capabilities; early permission refusal handled too |
| Individually exposed Webmastery tool failure | Different behavior from gateway depending on original error shape | Same error text/envelope and flag as gateway | Individual tool exposure is server configuration, not a new default server |
| Gateway success | Extra Adapter `success/data` wrapper | Unchanged | Parse exactly the gateway wrapper; do not recursively scan success data |
| Foreign plugin tools/abilities | Adapter behavior | Unchanged, even for identical-looking failure arrays | Namespace/backing-ability isolation; no global Adapter interception |
| Bulk publish/trash | Successful batch summary with inline per-ID failures | Same summary/counts/successes; failures are `{id,code,reason,message,details}` | Non-atomic; batch `success:true` does not mean every item succeeded |
| Plain external `WP_Error` | Could disclose arbitrary provider diagnostics | `upstream_failed/external_error`, fixed message, no provider data | Familiar codes such as `forbidden` do not establish trusted provenance |

Native callback helpers still use `WP_Error` internally where WordPress APIs
require it. Raw reflection of a callback is not a substitute for the registered
ability boundary. Locally authored errors use `local_error()`; normal providers
must not be relabeled as trusted just to retain their message or data.

Owned callback invocation delegates to core once. On WordPress 6.9, uncaught
callback exceptions become the same safe `ability_callback_exception` failure
that newer core versions provide. Exception messages/data never become client
diagnostics. Permission exceptions remain native `WP_Error` failures (default
status 502 for `upstream_failed`); explicit authorization denials retain 403.
Registered execution retains core's `ability_invalid_permissions` redaction.

## Client changes and recovery

1. Check HTTP and JSON-RPC failures first. Authentication, routing, malformed
   gateway input, and unregistered abilities are Adapter/core failures, not
   guaranteed Webmastery envelopes.
2. For a Webmastery MCP tool error, require `isError:true`, then JSON-decode the
   text content. Read `error.code` and `error.reason`, not a message substring.
3. For normal gateway success, unwrap its existing `data` once. Preserve the
   ability's own success payload, and inspect every bulk item/count.
4. Update old `error.code === "invalid_scheduled_date"` branches to
   `error.code === "invalid_input" && error.reason === "invalid_scheduled_date"`.
   Move failure context reads from `data` to `error.details`.
5. Reload state/hashes before retrying precondition failures. Do not blindly
   retry destructive or partially successful bulk operations. Forbidden,
   invalid input, unsupported, and conflict failures require a changed request
   or authorized human decision, not automatic escalation.

Example unchanged scheduling input, using the existing gateway:

```json
{"name":"mcp-adapter-execute-ability","arguments":{"ability_name":"webmastery-site-toolkit-for-mcp/create-post","parameters":{"title":"Migration check","status":"future","scheduled_date":"bad date"}}}
```

With an authorized Editor, this returns a tool error whose text decodes to
`success:false`, code `invalid_input`, and reason `invalid_scheduled_date`.
It must not create a post. A denied Subscriber is rejected earlier with code
`forbidden`. Core registered execution deliberately redacts callback permission
details to reason `ability_invalid_permissions`; Adapter's earlier permission
check can retain a specific safe local permission reason.

Example bulk failure entry:

```json
{"id":42,"code":"precondition_failed","reason":"trash_disabled","message":"Trash is disabled.","details":{}}
```

An all-failed batch still has `success:true`, `success_count:0`, and a failure
for each processed ID. Errors are inline, not a top-level MCP tool failure.

## MCP Adapter 0.6.1 limitation and upstream follow-up

The version-pinned `ToolsHandler::call_tool()` checks permissions **before**
`mcp_adapter_tool_call_result`. That result filter receives result, arguments,
tool name, actual tool object, and server. `create_error_result()` serializes only
the native error message: code/data are discarded. Structured content is null
inside the Adapter, but HTTP serialization omits the `structuredContent` key.
The gateway additionally wraps ordinary results.

The plugin therefore encodes the full canonical envelope as the native carrier
message, including for early permission failures. Its result filter examines
the actual backing ability and, for the Adapter execute gateway, exactly one
owned target result. It does not alter foreign tools, bypass permissions, or
rewrite REST responses.

Expected error wire shape (the text string contains the envelope above):

```json
{"content":[{"type":"text","text":"{\"success\":false,\"error\":{\"code\":\"invalid_input\",\"reason\":\"invalid_meta_key\",\"message\":\"Invalid metadata key.\",\"details\":{}}}"}],"isError":true}
```

There is **no claim of structured error `structuredContent` support**. An
interoperable parser can accept either an omitted key or explicit null; the
real 0.6.1 HTTP evidence records omission, not an explicit-null wire field. An
upstream enhancement should preserve native code/data in structured errors and
provide a final error hook covering early permission rejections. Filing that
upstream issue is deferred pending maintainer approval; this development change
does not upgrade or patch the Adapter dependency. Reproduce with the scheduling
call above and a Subscriber permission denial on both gateway and individual
tools; retain raw responses, installed handler hash/version, and redacted
negative controls. Runtime evidence belongs to the PR's QA artifacts, not to a
claim that source inspection alone proves the wire behavior.

## Destructive-operation interlocks

This is a separate breaking input contract, not merely error normalization.
The five affected abilities retain their WordPress capabilities. Single
post/page/CPT soft-delete inputs and disabled-trash refusal are unchanged.

| Surface | Before | 3.0 development |
| --- | --- | --- |
| Permanent media/category/tag deletion | ID only | ID and exact JSON `confirm:true` required |
| Bulk publish/trash | IDs without a raw upper bound or confirmation | `confirm:true`, 1-100 raw IDs; normalized duplicates processed once |
| Bulk preview | No preview | Optional boolean `dry_run:false` by default; true checks eligibility with no mutation and adds `data.dry_run:true` |
| Media references | No pre-deletion reference gate | Known featured-image/content URL/GUID references refuse unless boolean `force:true`; default false |
| Successful media deletion | `{id,deleted}` | `{id,deleted,in_use}` with boolean known-reference result, even when forced |
| Bulk counts | One entry per supplied ID | `requested`, successes, and failures count unique normalized IDs; invalid types rejected before work |

Strings (`"true"`), numbers (`1`), false, null, and missing confirmation are not
confirmation. Direct callback rejection uses `precondition_failed` /
`missing_confirmation`. Core schema validation runs first on registered
execution and can instead report `invalid_input` / `ability_invalid_input`.
Non-boolean `dry_run` or media `force` returns invalid input, not coerced truth.
Direct oversized batches return `invalid_input` / `too_many_ids` with
`error.details:{"limit":100}`; the schema's `maxItems` can reject earlier.
A 101-entry array containing the same ID still exceeds the limit.

Preview first, then obtain independent approval for the actual operation:

```json
{"ability_name":"webmastery-site-toolkit-for-mcp/bulk-publish-posts","parameters":{"ids":[123,456],"confirm":true,"dry_run":true}}
{"ability_name":"webmastery-site-toolkit-for-mcp/bulk-publish-posts","parameters":{"ids":[123,456],"confirm":true,"dry_run":false}}
```

Previews require confirmation and the same permissions as execution. They run
all applicable per-ID type/capability/status/disabled-trash checks but invoke
no post/meta/term/scheduling mutations or write hooks. Their successes mean
**would act**; failures retain `{id,code,reason,message,details:{}}`. The top-level
`success:true` means the batch was processed, even if every ID failed. Inspect
both counts and every item. No transaction, reservation, or guaranteed later
write is implied: concurrent edits, storage failures, and third-party write
hooks can still change a real execution.

For media, first call with the intended ID and `confirm:true`:

```json
{"ability_name":"webmastery-site-toolkit-for-mcp/delete-media","parameters":{"media_id":789,"confirm":true}}
```

`precondition_failed/media_in_use` requires an intentional decision, not an
automatic retry with force. If deletion of known referenced media is separately
approved, add `force:true`. It bypasses only a positive reference finding;
`delete_post` permission and a successful scan remain mandatory. Query errors
return `upstream_failed/content_hygiene_query_failed` without SQL diagnostics.
Successful forced deletion still reports truthful `in_use:true`.

The shared reference helper checks `_thumbnail_id` metadata and literal
attachment URL/GUID matches in post content, just as orphan-media inspection
does. Custom metadata, serialized settings, derivative URLs, external sites,
and concurrent changes are not universal-proof coverage. Do not interpret
`in_use:false` as proof that nobody uses a file.

For term deletion, add `confirm:true` to existing requests, for example
`{"category_id":123,"confirm":true}`. Registered custom taxonomy capabilities,
per-term denial, default-category refusal, and existing deletion results remain
authoritative. These safety inputs do not grant capabilities, establish human
intent, or prevent prompt injection; client-side approval must be independent
of retrieved content and bound to the exact action and IDs.

## Database diagnostic table privacy

This is a breaking **3.0 development** change; the 2.6.0 contract still
uses physical names. `database-health` continues to require `manage_options`,
including a direct execute-time denial before any diagnostic queries.

| Input | `table_sizes[].table` | Disclosure |
| --- | --- | --- |
| Omitted / `{}` / `{"include_table_names":false}` | Core logical names such as `posts`; other tables become `custom_table_1`, `custom_table_2`, etc. | No configured prefix or custom/plugin identifiers |
| `{"include_table_names":true}` | Original physical table names | Deliberately sends the prefix and plugin/custom identifiers to the model provider |
| Nonboolean flag, including `"true"`, `1`, or `null` | Failure; no table data | Canonical `invalid_input`; no coercion, including direct callbacks |
| Caller lacking `manage_options`, either valid mode | Failure; no table data | Canonical `forbidden` |

Every row adds boolean `is_core_table`. Classification matches the actual
WordPress physical table mapping for the current blog and global tables,
including custom user-table mappings, not a suffix such as `_posts`. Only safe
core logical labels are published; plugin-added mapping names are not trusted
as public labels. Tables outside the existing current-prefix SQL selection are
not added, including global tables outside a subsite's prefix.

Counts, bytes, result ordering, other diagnostic fields, and SQL query scope
are unchanged. Opaque custom labels are assigned in response order and restart
for each response: they are **not hashes and not stable cross-report IDs**.
Update clients that join reports by physical name; use raw-name opt-in only
when that diagnostic disclosure is intended, not as an automatic compatibility
fallback. Both modes continue to omit passwords, filesystem paths, and raw SQL
errors. Existing safe contextual query failures and security-audit HTTPS/log
behavior are unchanged.

On a disposable site with a custom prefix and an owned plugin-named table,
compare Administrator default, explicit-false, and explicit-true calls. Verify
full-payload identifier absence by default, physical names only on opt-in,
exact row-by-row metric/order parity, and Subscriber denials in both modes.
Also test omitted registered arguments and MCP empty-object arguments; the
schema's top-level empty-array PHP default represents empty object input for
WordPress validation and does not coerce a supplied flag.

## Metadata and SEO authorization

This separate breaking 3.0 change modifies input and SEO success contracts.
The unchanged-success statements in the error-normalization section do not
apply to these explicitly documented metadata changes. Released 2.6 behavior
and release notes remain historical; no version or dependency upgrade is
implied by this development guide.

### Create and general update: no combined metadata

All `create-post`, `update-post`, `create-page`, `update-page`, and dynamically
registered `create-cpt-*` / `update-cpt-*` abilities reject the **presence** of:

- `meta` or `meta_input`;
- every top-level field starting `yoast_` or `seopress_`, including unknown aliases;
- raw top-level keys starting `_yoast_wpseo_` or `_seopress_`.

Null, empty objects/arrays/strings, false, zero, absent stored keys, and
unchanged values do not exempt a supplied field. Administrators are subject to
the same contract. Rejection occurs before post/meta/term writes, scheduled
events, and save hooks. There is no speculative object creation, ID-zero
provider authorization, or rollback-based preflight.

Direct callback execution returns code `invalid_input`, reason
`metadata_requires_separate_call`, and `error.details.fields` containing only
the rejected field names, never their supplied values. Native schema or
permission checks can reject earlier; see the exact boundary table below.
Plain post, page, and CPT operations
retain their existing content, status, parent, taxonomy, and scheduling checks.
Schemas no longer advertise combined metadata or SEO alias properties.

### Strict input schemas and raw permissions

Fixed-property input objects now reject unknown keys. Built-in posts and
nonhierarchical CPT create/update calls must omit `parent`: even `parent:0`
or `parent:null` is an unadvertised property. Pages and hierarchical CPTs
retain advertised zero-detach and omitted-parent behavior. The already-landed
parent permission, type, hierarchy, existence, and cycle checks are not new
work and are not relaxed.

Supply exact enum strings, actual JSON integers for IDs, and actual booleans
for flags. Invalid strings are rejected before sanitization or query building;
for example, `order:"DESC!"` cannot become `"DESC"`. Omitted optional fields
keep existing defaults; explicit null does not mean omission unless nullable.
Input-free abilities accept omitted input or an empty object and reject extra
properties. PHP's empty associative array represents either decoded `{}` or
`[]`; the callback guard accepts that empty representation.

The registration-time guard runs for both callbacks because Adapter 0.6.1
can invoke `check_permissions()` before `execute()` validates the schema.
Malformed permissions return native `WP_Error`, never a truthy error array;
direct execution returns the canonical seven-code envelope with object
`details`. Existing callback success data and effective authorization remain
unchanged. Existing destructive guards retain strict confirmation even during
preview, 100 raw IDs before deduplication, strict optional flags, object
capabilities, and media/trash semantics.

| Input failure | Native ability execution | Direct execute / raw permission / adapter permission boundary |
| --- | --- | --- |
| Unknown property or invalid enum rejected by core schema | `invalid_input` / `ability_invalid_input` | `invalid_input` / `ability_invalid_input` |
| Combined metadata or reserved SEO field | `invalid_input` / `ability_invalid_input` | `invalid_input` / `metadata_requires_separate_call`; presence-only batched field names, no values |
| Integer ID supplied as a numeric string | Core may accept the coercible integer, then redact raw permission rejection to `forbidden` / `ability_invalid_permissions` | `invalid_input` / `ability_invalid_input` |
| Invalid destructive confirmation/flags/bounds | Core schema errors use `ability_invalid_input`; permission redaction still applies when reached | Direct execute preserves the existing operation-specific preflight reason; raw permission uses `ability_invalid_input` |

These layer-specific expectations are source-derived and covered in isolated
tests; actual gateway/individual runtime evidence must still be collected on
the integrated candidate. Do not broaden assertions to accept arbitrary reasons.

Only fixed object property sets are automatically closed. Arbitrary
`meta_value` JSON (including nested/numeric-key objects), dynamic
`taxonomy_terms` maps with their integer-array item schemas, unconstrained
objects, and explicitly open extension maps remain supported. Existing
registered-taxonomy/key authorization still applies. Block attribute payloads
are not closed by this helper.

The helper intentionally implements structural/type/enum/required/range/item
checks, not all JSON Schema features: WordPress and existing domain validators
remain responsible for formats and other keywords. Optional output schemas
are deferred because provider/error responses are polymorphic and the separate
list-performance work changes projections. A naive required-`data` success
schema would misrepresent these contracts.

### Draft, separate writes, then publish

For example, send these calls in sequence, using the real returned draft ID:

```json
{"ability_name":"webmastery-site-toolkit-for-mcp/create-post","parameters":{"title":"Draft title","content":"Draft content","status":"draft"}}
{"ability_name":"webmastery-site-toolkit-for-mcp/update-post-meta","parameters":{"post_id":123,"meta_key":"_yoast_wpseo_metadesc","meta_value":"Description"}}
{"ability_name":"webmastery-site-toolkit-for-mcp/update-post","parameters":{"post_id":123,"status":"publish"}}
```

Check success and sanitized `data.current_value` after **each** metadata write.
Optionally read back an explicit key through `get-post-meta`. Publish only
after all required keys succeeded. For multiple keys, issue one separately
authorized write per key; this is not a batch transaction. If a later write
fails, the draft and earlier authorized writes remain. Do not publish on a
partial failure and do not retry the old combined payload. Existing objects
likewise require separate content and metadata calls.

Use the same exact-key workflow for pages and CPT objects. The standalone
metadata tools retain their key eligibility, structured public values,
backslash preservation, and provider sanitization. Protected SEO values
retain scalar normalization. Updates require effective `edit_post_meta`,
deletes require `delete_post_meta`, and both require `edit_post` on the real
object. Registered global/subtype policies and `map_meta_cap` / `user_has_cap`
remain authoritative. An auth callback returning false alone is not always
a veto if WordPress permits explicit primitive grants; `do_not_allow` wins.
Yoast's add/edit and delete policies may differ.

Only the existing supported, genuinely unregistered SEO compatibility keys
without global/subtype authorization hooks receive the temporary default.
The exact temporary filter is removed in `finally`. No fallback is extended
to score-only or other read-only keys.

### Separate SEO read contracts

Every exact metadata key is checked with effective `edit_post` and
`edit_post_meta` before reading. This conservative plugin read policy is not
a generic WordPress read-meta capability and does not imply that editing a
public page grants access to all its metadata.

| Ability | Changed successful projection |
| --- | --- |
| `get-yoast-metadata` | Denied fields absent from both `metadata` and `raw_meta`; `unavailable_fields` identifies unavailable field names. `generated_head.available` is false with reason `key_authorization_unavailable`. |
| `get-seopress-metadata` | Same per-key omission and unavailable-field policy; no raw denied values. |
| `seo-analyze-post` | Denied metrics are absent. Authorized Yoast values retain precedence; authorized SEOPress values remain fallback. If no authorized nonempty value is known and a provider field is denied, omit its source and skip its check rather than reporting it missing. |
| `get-seo-scores`, `get-readability-scores` | Filter object and exact-score-key permission before `total`, `total_pages`, and slicing; read scores only for returned objects. |
| `seo-site-overview` | Counts describe bounded authorized observations, not metadata predicates or sitewide missing-field totals. |

Unavailable field errors use code `forbidden`, reason `metadata_not_readable`,
a fixed message, and empty object `details`. They carry no stored value,
length, source, or derived score. Fully authorized analysis retains its
previous response keys and diagnostics. When fields are denied it additionally
reports `unavailable_fields` and `unevaluable_checks`; its score describes
only the checks actually evaluated, not a complete SEO grade.

Generated Yoast HTML/JSON is deliberately not fetched: provider extensions
can add unknown metadata, so checking a fixed list does not authorize that
opaque output. There is no opt-in fallback. URL-only requests return
`unsupported` / `generated_head_key_authorization_unavailable` after the
existing Administrator permission check.

Overview selects at most 100 published post/page IDs with `ID ASC`, one
query, and no metadata predicate. Each missing-field result has `count`,
at most 20 `ids`, and `observed_count` for authorized observations. The outer
`observation_scope` is
`{"mode":"sample","post_limit":100,"ordering":"ID ASC","counts_are_sitewide":false}`.
Denied observations contribute neither missing counts nor IDs nor
denominators. A zero denominator means no authorized evidence, not good
health. Independent native `total_published.posts`/`.pages` counts remain.
The 101st candidate is not inspected even if every earlier candidate is denied.
